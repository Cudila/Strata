# strata-nemotron: review of decode, short turns and vision (2026-10-22)

What was measured on the production setup, what changed, what was tried and dropped. The working notes (static
reading of the code, task lists, Russian run logs) are in `notes/` and `ru/`; the numbers below are the measured ones,
and anything that was only an estimate is called one.

All numbers: RTX 5090 32 GB, i7-14700KF, 128 GB DDR5-5200, PCIe 5.0, Linux; the engine as in
`strata-nemotron.example.json` (`--spec 5 --spec-min-p 0.8 --skip-w 0.4 --prefetch 0 --evict lfu`, 1M context, vision
encoder on the GPU, 116 expert slots a layer). The server's usual neighbours (llama-swap) were stopped and the GPU
locked for each run; the `--prompt-skip-w` sweep (section 4) still shared RAM and some VRAM with other jobs.

## 1. What a decode window costs (before any change)

32K prompt, warm, 300 generated tokens, greedy, 93 windows. A "window" is one MTP verify step with its drafts.

| part of a window | ms | share |
|---|---:|---:|
| drafts (up to 5 MTP steps) | 2.2 | 12% |
| verify forward | 15.2 | 84% |
| &nbsp;&nbsp;routed experts | 7.9 | 43% |
| &nbsp;&nbsp;Mamba (40 blocks) | 3.1 | 17% |
| &nbsp;&nbsp;dense + router | 1.8 | 10% |
| &nbsp;&nbsp;fc2 + shared expert | 1.5 | 8% |
| &nbsp;&nbsp;attention (8 blocks) | 0.8 | 4% |
| rest (pick, rollback, MTP bookkeeping) | 0.6 | 3% |
| **window** | **18.2** | 3.2–4.4 tokens: 177–206 tok/s |

How it was taken: `STRATA_NEMO_HOSTPROF=1` for the draft / verify / rest split, `STRATA_NEMO_PROFILE=1` for the phases
inside verify (it syncs at phase borders; the sum, 15.8 ms, matches the 15.2 ms verify), and an nsys trace of one
300-token warm decode (89 windows).

- Per window: 926 kernel launches, 50 `cudaStreamSynchronize`, 324 async copies. Two kernels, `gemv_kernel` and
  `tc_tiled_kernel`, are 70% of the wall time. The GPU is idle 12.8% of the window (~2.3 ms).
- Decode speed is flat from 6K to 83K tokens (177–206 tok/s). The spread between identical runs (176–190 tok/s at 32K)
  is as large as the difference between contexts.
- Sampled decode (temperature 1.0, top_p 0.95, top_k 64): 174.6 tok/s against 185.1 at temperature 0 (6 runs each).
  The window takes the same time (17.5 against 17.9 ms); the loss is fewer tokens a window (3.06 against 3.31).
- A short turn after a 75K prefix (30–1,500 new tokens): time to first token 230–540 ms, fitted as 281 ms + 0.14 ms per
  prompt token. About 50 ms of that is outside the engine (tokenizing, template, transfer). Inside the engine a 100–576
  token turn moves 8.5–14.3 GB over PCIe (5,660–9,368 copies) in 190–316 ms, while the kernels take 76–102 ms. So a
  short turn is bound by expert copies, as the notes say for short prompts.
- A request from another conversation in the middle of a session replaced the single snapshot: the next turn
  (30 new tokens) read all 78K tokens again, 7,693 ms, against 232 ms without the side request.
- Vision, 1920×1080 PNG (2,040 tokens): the encoder call took 240 ms, of which the CPU resize was ~56 ms; the cold
  time to first token was ~1.0 s.

## 2. What changed

| change | where | default |
|---|---|---|
| Checkpoints inside a conversation, parking of conversations (`CONVERSATION_CACHE.md`) | `--prompt-cache N`, `--prompt-cache-every M`, `--conversation-cache-mib X` | off in the engine; on in the example config (8, 16384, 3000) |
| `--prompt-skip-w` 0.3 → 0.4 (section 4) | engine flag | example config now 0.4; the engine's own default is unchanged |
| strata-vision: threaded resize, an unchanged axis skipped; WebP / TIFF / EXIF-rotated JPEG handed over as BMP; per-stage timings on stderr (`VISION_CPU` in `ru/`) | `tools/vision/strata_vision.cpp`, `serve/server.py` | always on |
| Five decode switches (section 3) | environment variables | off |

Vision, details. The resize passes run over rows on `max(4, cores/2)` threads (14 here) with the same arithmetic as
before, and an axis whose length does not change is skipped (its weights are exactly 0, 1, 0, 0). The `.sve` files are
byte-identical to the old build on 5 test pictures. Resize on 1920×1080 went from 41.3 to 19.5 ms, on 2560×1440 from
81.3 to 38.2 ms; the whole encoder call from 240 to 221 ms and from 469 to 424 ms (mean of the 2nd and 3rd call of a
process). The server used to convert WebP, TIFF and EXIF-rotated JPEG to PNG; it now writes an uncompressed BMP
(Pillow's PNG encode of a 1024×768 picture is ~13 ms; the BMP takes 2–10 ms). Embeddings of a lossless WebP and a
TIFF are byte-identical to those of the PNG; lossy or rotated inputs differ, as they must. The encoder's per-token
cosine against NVIDIA's code was not re-run (the checkpoint folder here holds only 5 of 63 shards); the check used was
byte equality with the old build, whose cosine was ≥ 0.998.

## 3. Decode switches (batch 1): in the noise, off

Five environment variables, all off by default, so the default path is unchanged. None of them is part of the
published setup.

| variable | what it does |
|---|---|
| `STRATA_NEMO_SHARED_EARLY` | the shared expert runs right after the ids are queued for the host; the host waits on an event, not on the whole stream. Adds in `x` change order, so token ids change |
| `STRATA_NEMO_LFU_FAST` | the LFU decay table is computed once per search pass. `STRATA_NEMO_LFU_CHECK=1` compares with the old search: 1,835 searches, 0 differences |
| `STRATA_NEMO_MAMBA_SWAP` | the verify window writes the new Mamba state into a second buffer and the pointers are swapped on full acceptance, instead of copying 165 MB before every window |
| `STRATA_NEMO_GPU_TOPK` | the top-k of the sampled rows is selected on the GPU; one pinned copy per window instead of a 512 KB pageable copy per row |
| `STRATA_NEMO_MTP_EVENT` | an event replaces a stream sync at the start of the MTP rows |

Token ids against the switch off (32K bench; the expert-slot count has to be equal, because the cache contents change
the text): LFU_FAST and MAMBA_SWAP identical at 152 slots; GPU_TOPK identical at temperature 1.0 with a seed, 152
slots; MTP_EVENT identical to the run with the first two on (156 slots), not compared with "off" directly.
SHARED_EARLY changes the ids, as expected from the changed order of floating-point adds. `mamba_parity` and
`moe_parity` were built but not run after these changes.

Speed: no measurable effect. The final A/B ran the new build with all five switches on. Warm decode at temperature 0:
181.1 → 176.4 tok/s at 6K (−2.6%), 185.8 → 182.2 at 32K (−1.9%); at temperature 1.0 and 32K 169.6 → 171.1 (+0.9%).
The spread between identical runs of one build is 8–12%, so none of these differences is real. The earlier one-off
bench runs gave +2–4% for two of the switches at an equal expert-slot count, which is also inside the spread. Tokens
a window and draft acceptance were the same within noise (3.17 → 3.47 and 81% → 81% at 32K).

## 4. `--prompt-skip-w`: 0.3 → 0.4

`--prompt-skip-w τ` skips a cache miss of a short prompt (≤ `--prompt-skip-max` rows) whose routing weight is below τ.
A higher τ copies fewer experts, so a short turn gets faster, and the output gets a little worse.

Measured with a 16,448-token slice of the wikitext-2 test set cut into 16 chunks of 1,024 tokens (`--ppl --ctx 1024
--chunks 16`, `--evict lfu --prompt-skip-max 8192`, `--max-context 4096`), and time to first token of short turns after
a 75K prefix through the server (median of 3 requests; prompt_n 112 / 197 / 580 / 2,583 tokens; one server run per τ;
the GPU and RAM were shared with other jobs, so treat the milliseconds as indicative).

| τ | PPL (ctx 1024) | PPL against τ = 0 | TTFT, +30 tokens, ms | +100 | +400 | +2000 |
|---|---:|---:|---:|---:|---:|---:|
| 0 (off) | 3.0351 | ×1.000 | 1,106 | 1,208 | 1,293 | 1,316 |
| 0.3 (before) | 3.0484 | ×1.004 | 289 | 326 | 402 | 596 |
| **0.4 (now)** | **3.0728** | **×1.012** | **159** | **181** | **220** | **434** |
| 0.5 | 3.3015 | ×1.088 | 137 | 148 | 178 | 380 |
| 0.6 | 4.1321 | ×1.361 | 129 | 138 | 156 | 354 |

The rule used: a change is taken when the time to first token falls by a larger percentage than the PPL rises. 0.3 → 0.4
saves 44–45% on turns of 30–400 tokens (27% at 2,000) for +0.8% PPL. 0.5 and 0.6 also pass that rule on paper, but cost
×1.088 and ×1.361 on this test; 0.4 is the highest value tested whose PPL cost stays near 1%. The PPL is measured on
1,024-token chunks, not on an agent session at 75K, so it shows the size of the effect on short prompts and is not a
quality measure of a long session. For the full test of the 0.3 value (×1.005) see `ENGINE_V3.md`.

## 5. Final A/B: before and after

Two server runs on the same machine, about 15 minutes apart, each arm in its own run. Before: the production tree
(`--prompt-skip-w 0.3`, no conversation cache). After: this tree with `--prompt-skip-w 0.4 --prompt-cache 8
--conversation-cache-mib 3000`, and the five switches of section 3 on. Both started with 116 expert slots (K/V
65,536 cells, growing to 131,072 cells with 112 slots).

Short turns after a 75K prefix (`max_tokens 1`; median of 2 repeats; ms):

| new tokens | TTFT before | TTFT after | change | prompt tokens read before / after |
|---|---:|---:|---:|---:|
| first turn after the cold prefix | 507 | 327 | −36% | 110 / 65 |
| +30 | 300 | 160 | −47% | 112 / 67 |
| +100 | 353 | 186 | −47% | 198 / 153 |
| +400 | 417 | 227 | −46% | 577 / 532 |
| +1,500 | 537 | 350 | −35% | 1,951 / 1,906 |
| cold 75K prefix | 7,516 | 7,633 | +1.6% | 75,474 / 75,474 |

The ~45 tokens of template and answer that were re-read after every turn are no longer read; that is the "after
generation" checkpoint. The rest of the gain probably comes from `--prompt-skip-w 0.4`; the two were not measured apart.

A side request in the middle of a session (a 4,182-token request from another conversation, then +30 tokens on the
~81K session):

| | TTFT before | TTFT after | tokens read before / after |
|---|---:|---:|---:|
| the other conversation's request | 1,002 | 842 | 4,182 / 4,182 |
| +30 on the session | 7,803 | 204 (−97%) | 81,301 / 59 |

A branch (the same ~81K history, a different last message of +200 tokens): TTFT 7,844 → 235 ms (−97%); tokens read
81,530 → 288.

Pictures (PNG, a pixel-edited copy for each "cold" request, streaming; two runs each):

| picture | TTFT before | TTFT after | change | prompt ms before → after |
|---|---:|---:|---:|---:|
| 1920×1080 cold | 1,347 / 1,024 | 1,058 / 774 | −22% / −24% | 747 → 440 / 698 → 388 |
| 1920×1080, second turn, same picture | 843 / 836 | 495 / 479 | −41% / −43% | 694 → 340 / 671 → 326 |
| 2560×1440 cold | 1,490 / 1,354 | 1,167 / 1,126 | −22% / −17% | 778 → 451 / 773 → 481 |
| 2560×1440, second turn | 1,036 / 984 | 692 / 705 | −33% / −28% | 804 → 480 / 773 → 481 |

Both builds encode the picture again on the second turn; there is no cache of picture embeddings in this set. (The
"prompt ms" column includes the encode.) Inside the server the encoder is slower than alone (246–431 ms at 1920×1080,
431–490 ms at 2560×1440, against 181 and 358 ms for the encode stage in the standalone runs), because it shares the GPU
with the engine.

Decode did not change: at 6K, 32K and 32K with temperature 1.0 the differences are −2.6%, −1.9% and +0.9% against a
spread of 8–12%. Cold prefill: 6K 1,489 → 1,382 ms, 32K 2,779 → 2,766 ms. A warm request's prompt step is 7–15 ms
slower (41–49 against 31–35 ms: restoring the checkpoint and parking a copy of the conversation).

Text quality: greedy texts of one build are not deterministic even against themselves (the expert cache and `--skip-w`
depend on the history). Common prefixes of 300-token texts, in characters: 25–309 between runs of the old build,
27–217 between runs of the new one, 25–86 between old and new at 6K; 47–155, 2–53 and 2–42 at 32K. The old-against-new
difference is of the size of the run-to-run difference, and every text is a valid summary of the same document. PPL at
`--prompt-skip-w 0.4` was not repeated for the A/B (section 4).

No crashes or engine errors in the new build.

## 6. Tried and dropped

| idea | result | decision |
|---|---|---|
| **Read each routed expert once per verify window** (`STRATA_NEMO_EXPERT_ROWS=1`; one launch block per distinct expert, up to 8 rows each) | Same ids as the old path (greedy and temperature 1.0), but slower: 177 / 162 / 185 tok/s against 191 / 199 / 193 with the switch off (the 2nd and 3rd runs of a process have another cache state). nsys: `gemv_kernel` 569 ms over 83 windows with 26,318 launches, against 461 ms and 9,178 launches. Reason: three times the launches, each 13–39 µs; the 8-row class holds ~91 KB of shared memory, one block per SM. With `--skip-w 0.4` most window entries are skipped (96,151 skipped, 73,216 hits) and read a zero blob from L2, so there was little to save | not merged (the branch `strata-nemotron-expert` is not part of this tree). Untried: one launch with the row count read in the kernel; a mode for experts with ≥ 3 rows only; a run without `--skip-w` |
| **Q8_0 vision projector file** (`mmproj-Q8_0.gguf`, 922 MiB against 1.7 GB, made with llama-quantize in 11 s) | Encode 4–11% faster (e.g. 240 → 223 ms at 1920×1080), VRAM −786 MiB (2,886 → 2,100 MiB). Per-token cosine against the BF16 embeddings: mean 0.9996–0.9998, but the worst token is 0.99875 / 0.99696 / 0.98611 / 0.99629 / 0.94680 on the 640×480, 1024×768, 1920×1080 PNG, 1920×1080 JPEG and 2560×1440 pictures; the limit is 0.998, so 4 of 5 fail. End-to-end TTFT only 2–4% better, answers equal in meaning on the pictures tried (one sample each) | not taken. If the 786 MiB matter, check real documents and charts first |
| `--prompt-skip-w` 0.5 / 0.6 | −53…−56% / −55…−61% TTFT against 0.3, PPL ×1.088 / ×1.361 | not taken (section 4) |
| the five batch-1 switches as a default | no measurable speed-up (section 3) | left off |
| A CUDA graph for the decode window, "−3 ms" | not built. The window is 87% GPU-busy; the host's ~900 launches are ahead of the GPU between syncs, so launch cost is hidden. Removing every idle gap would save at most the 2.3 ms above | not pursued |

## 7. Not done

- Reading the images of a conversation per picture instead of one combined file, and loading only the unreused ones
  (estimated 30–80 ms per resident picture per turn; not measured).
- A cache of picture embeddings across turns (both builds encode a repeated picture again).
- libjpeg-turbo decoding in strata-vision, an F16 projector file, an elastic encoder that gives its VRAM back when idle.
- More than one server run per arm in the A/B: every figure above is one server run per arm, with the variation
  noted where it was seen.

## 8. Corrections made to the other docs

- `OPTIMIZATION_NOTES.md` section 5: the production setup (and the example config) runs `--prefetch 0`, the ×1.091
  row; the ×1.008 row is the precise mode.
- `VISION_MMPROJ.md` and `README.md`: "36–463 ms" is the whole encoder call (decode, resize, GPU encode, file write),
  not only the GPU.
- `tools/vision/strata_vision.cpp`: RADIO-H's attention head is 80 (1280/16), not 72; the comment came from another
  vision tower.
