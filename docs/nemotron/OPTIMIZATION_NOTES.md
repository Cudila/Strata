# Nemotron 3.5 Super на одной RTX 5090: тонкости оптимизации и что режет производительность

Сборник выводов, полученных при переносе Nemotron 3.5 Super VL (120B-A12B, гибрид Mamba-2 / MoE / attention) на
движок Strata на одной машине: RTX 5090 32 GB (sm_120), 128 GB DDR5-5200, PCIe 5, i7-14700KF. Цифры — замеры на этой
машине, если не сказано иное. Дополняется по ходу работы.

## 1. Железо: что на самом деле доступно

Рабочий стол на этой машине живёт на той же карте: kwin и портал захвата экрана (rustdesk) при нехватке VRAM
теряют буферы, а портал — разрешение на захват. Поэтому все слоты работают под `~/llm/vram-guard` (1 ГБ свободной
VRAM гарантированно), а движку остаётся `--vram-reserve-mib 1024`.

| ресурс | цифра | замечание |
|---|---:|---|
| PCIe 5 host→device | ~41 ГБ/с | при любом размере копии (замер); это и есть потолок «экспертов из RAM» |
| VRAM | ~1.5 ТБ/с | decode-GEMV упирается сюда |
| mma BF16 / FP16, FP32-сумма | 256 TFLOP/s | GeForce: FP32-аккумулятор на полной скорости только у BF16/FP16 |
| mma FP16, FP16-сумма | 512 TFLOP/s | вдвое быстрее, точность суммы — FP16 |
| mma FP8 e4m3, FP32-сумма | ~450 TFLOP/s | |
| mma FP8 e4m3, FP16-сумма | ~830–1020 TFLOP/s | |
| mma int8, int32-сумма | ~800–1020 TOP/s | точные суммы |
| mma NVFP4 (`kind::mxf4nvf4.block_scale`) | ~1610 TFLOP/s | только sm_120a, скейлы ue4m3 на 16 значений — ровно формат NVFP4 |
| FP64 | ~1/64 FP32 | double-аккумуляторы дороги по памяти и по счёту |

Вывод: на GeForce Blackwell «формат = скорость». BF16-путь (cuBLAS) упирается в ~150–235 TFLOP/s, FP4-путь даёт
~800 на реальной форме. Модель, которая уже NVFP4, надо исполнять на FP4 mma, а не расширять в BF16.

## 2. Архитектурные решения модели, которые режут производительность

1. **Плотная (full) attention в гибриде.** 8 слоёв attention на 88 блоков — мало по FLOPs на коротком контексте, но
   каждый шаг decode читает весь KV: на 1M это ~6.5 ГиБ (int8-K/FP16-V) на токен. Поэтому KV нельзя держать в RAM и
   стримить, как делает Strata для qwen3.8-flash-next (у той разреженная QSA-attention, decode читает выбранные ячейки):
   через PCIe это ~0.2 с на токен. KV обязан жить в VRAM и отнимает её у кэша экспертов (на 1M: 140 → 84 слота на слой).
   Prefill на длинном контексте квадратичен: на 1M attention — основное время (минуты).
2. **MoE 512 экспертов, top-22, ~3.1 МБ на эксперта (NVFP4).** 63 ГБ экспертов не помещаются в 32 ГБ; на decode-токен
   нужно 22 × 40 = 880 эксперт-слоёв. Top-22 — очень широкий роутинг: даже короткий prompt (100–500 токенов) задевает
   почти все 512 экспертов каждого слоя, то есть ~30–40 ГБ по PCIe ≈ 1 с. Время короткого prompt'а задаёт копирование,
   а не счёт. Чем шире top-k при том же числе экспертов, тем хуже prefill коротких промптов на картах с малым VRAM.
3. **Латентный MoE (4096 → 1024 → эксперты → 1024 → 4096).** Плюс: эксперт маленький (1024×2688), вход/выход 1024.
   Минус: две лишних плотных матрицы (fc1/fc2) на каждый MoE-слой и узкие GEMM экспертов (K = 1024), у которых
   меньше арифметической плотности.
4. **relu² у экспертов и shared-эксперта.** Распределение активаций после relu² тяжелохвостое (вход down-проекции) —
   неудобно для 4-битного квантования активаций; на практике W4A4 стоил ×1.003 PPL, но вход up-проекции экспертов
   (латент) оказался самым чувствительным (×1.004 из общих ×1.006 в эмуляции).
5. **Mamba-2 с 128 головами × 64, state 128, 8 групп.** Рекуррентность: последовательный scan на prefill медленный
   и упирается в задержки, нужен чанковый SSD; состояние надо снимать/восстанавливать при откате черновиков MTP.
   Для MTP-спекуляции нужен повтор conv/scan принятых строк — Mamba нельзя «откатить» дешевле.
6. **NoPE attention с GQA 32:2 и head_dim 128.** Плюс: нет RoPE, 16 голов делят одну KV-голову (варп = 16 голов
   одного токена, ключ читается один раз). Минус: всего 2 KV-головы — мало параллелизма по головам в decode, нужен
   split-K по ключам.
7. **Смешанный чекпоинт** (эксперты NVFP4, Mamba in/out и attention FP8 per-tensor, остальное BF16): FP8-слоям нет
   прямого быстрого пути в llama.cpp-формате; решение — in/out_proj в NVFP4 (PPL +1.6% вместе с attn в Q8_0).
8. **MTP-блок со своими 512 экспертами** (1.6 ГБ резидентно): ускоряет decode в 1.7–1.9 раза, но забирает ~13
   слотов кэша на слой, что заметно бьёт по короткому prompt'у (тот упирается в копии).

## 3. Тонкости, без понимания которых не оптимизировать

### Decode
- Вес маршрутизации — лучший критерий пропуска промаха: эксперт вне VRAM с весом < 0.4 во всех строках окна не
  копируется (PPL ×1.005). Пропуск по рангу (как в Strata) при той же скорости хуже.
- LFU с затуханием 0.97 даёт −7% промахов против LRU; статическое размещение по частоте хуже LRU; Belady −55%
  (потолок, недостижим).
- Предзагрузка по предсказанию (роутер следующего слоя на текущем остатке) помогает без пропуска промахов, но вместе
  с ним вредит вдвое: предсказанные эксперты — те, что и так пропустили бы.
- Плиточный формат для tensor-core GEMV: веса переупаковываются при загрузке так, чтобы линия варпа читала ровно свой
  B-фрагмент mma.m16n8k16 — тогда M = 1..8 стоит почти как M = 1 и окно проверки MTP почти бесплатно.
- Окно проверки побитно совпадает с decode, только если каждая строка считается независимо от M (свой порядок сумм).
  Это проверяемое свойство (greedy со спекуляцией = обычный decode), оно ловит много ошибок.
- Attention в decode на длинном контексте: CUDA-ядро с warp-reduction на каждый (ключ, токен окна) упирается в счёт,
  а не в память; tensor-core split-K, где блок читает ключ один раз для всех токенов окна, — вдвое быстрее окно.

### Prefill
- Копии экспертов должны идти параллельно счёту: отдельный поток, кольцо блобов, события освобождения. Сначала
  считать попадания (они в VRAM), промахи — по мере прихода; следующий слой планировать заранее (на большом чанке
  нужны почти все эксперты — копировать вслепую).
- Порядок суммирования вкладов экспертов зависит от того, что лежит в кэше, если считать попадания первыми, — prompt
  становится недетерминированным (PPL «гуляет» на 0.1% между прогонами, ломается совпадение спекуляции). Лечится
  суммированием в double (сумма 22 точных произведений не зависит от порядка).
- Pageable `cudaMemcpyAsync` синхронен: одна такая копия метаданных на группу экспертов останавливала хост и
  оставляла GPU без работы (простой 2.4 с на 8K). Всё, что копируется на каждом шаге, — через pinned-память.
- FP4 GEMM: главное — глубина k на стадию между `__syncthreads`. 64 значения на стадию — 390 TFLOP/s, 128 — 790.
  Обе операнды в «естественном» порядке полубайтов позволяют грузить фрагменты `ldmatrix` как b16-матрицы.
- Короткий prompt упирается в PCIe, длинный — в счёт. Размер чанка: 16K вдвое уменьшает копии на токен для длинных,
  но буферы чанка отнимают ~1 ГБ у кэша; хвосты буферов можно отдавать кэшу в долг, пока чанк короткий.
- Один эксперт может получить все строки чанка: буферы группы должны вмещать весь чанк (была запись за границу при
  чанке 16K).
- Mamba scan: последовательный вариант упирается не в шаффлы, а в зависимые подгрузки тайла из глобальной памяти;
  предвыборка следующего тайла в регистры дала больше, чем любые правки арифметики. Чанковый SSD в FP32 — ещё ×2.
- Квантование активаций в W4A4 лучше проверять эмуляцией (fake-quant в BF16-пути) до написания ядра; эмуляция
  с двойным округлением даже пессимистичнее реального ядра (×1.0064 против ×1.003).

### Attention на tensor cores
- int8 для Q·K с одним скейлом на вектор: ошибка выхода ~0.3% (BF16 — 0.13%, FP8 e4m3 — 1.6%). P в 8 битах
  (u8 или e4m3) — 1.7–2%, поэтому P·V в FP16 с FP16-суммой на тайл (0.32%).
- int8-K в кэше заодно уменьшает KV на четверть и вдвое — чтение K в decode.
- Упор ядра — регистры (~200 на поток): один блок из 8 варпов на SM, и `__syncthreads` на каждом тайле выравнивает
  варпы, так что mma и softmax не перекрываются (~40% теоретического потолка).

### Где на самом деле уходит время (замеры, а не догадки)
- Отключение частей ядра — дешёвый профилировщик, когда нет доступа к счётчикам (ncu требует прав): attention без
  обоих mma всё равно тратила 43 из 68 мс — значит, упор не в tensor cores. Замер фаз через `clock64` показал 25%
  «ожидания данных», которое оказалось адресной арифметикой загрузчика (деления и пересчёт страниц на каждый
  16-байтный кусок); после упрощения доля упала до 16%, а общее время почти не изменилось — фазы упираются в
  задержки при 2 варпах на планировщик, и сэкономленное время перетекает в соседние.
- Ограничение регистров (`__launch_bounds__(256, 2)`) ради 2 блоков на SM даёт спиллы и не ускоряет.
- Квантование активаций упиралось в память, а не в счёт: выход up-проекции экспертов в FP32 — ~3.9 ГБ на слой при
  чанке 16K. BF16-выход (relu² уже применён, дальше всё равно 4 бита) вдвое сокращает этот круг.
- Сумма вкладов экспертов «по ходу групп» гоняет 8-килобайтную строку-аккумулятор на каждую пару (токен, группа)
  ради 1–2 строк вклада. Писать выход down-GEMM сразу в слот (токен, ранг) и один раз суммировать 22 слота в
  порядке рангов — и быстрее (10.4K т/с против 8.6K на 32K), и детерминировано без double.
- Перепаковка весов экспертов в другой формат на каждой группе стоит дорого на коротких промптах (там почти все
  эксперты — попадания с 1–5 строками): там GEMM должен читать формат хранения сам. На длинных выгоднее один раз
  перепаковать и пустить быстрый загрузчик; 4-байтные cp.async (36-байтные блоки ggml не выровнены на 16) хуже обоих.
- PCIe: обычная pinned-память даёт 45–46 ГБ/с, закреплённое отображение файла — ~41–45; это потолок «экспертов из
  RAM» на этой платформе.

### MTP
- Окно внимания MTP-блока (черновик смотрит только последние W ячеек): prefill −4.5% при W = 8K, но принятие
  черновиков нестабильно (на длинном тексте с повторами W = 32K обрушило принятие с 4.6 до 2.6 токена на окно) —
  выключено.
- Плато настроек: длина черновика 4–7 × порог 0.7–0.9 дают 155–163 т/с, разница в шуме сэмплинга.

### Третья волна (19.10): что дало и что нет
- **Где предел prefill на 16K–64K.** Профиль чанка 16K (тёплый кэш): ядра ~1.17 с, копии экспертов по PCIe ~1.0 с
  (46 ГБ), простой 25–45 мс. Оба ресурса заняты почти целиком, поэтому ускорение одного ядра на N мс даёт в сумме
  2–4 раза меньше: 77 мс экономии на GEMM attention/fc превратились в ~6 мс на промпт. Чанк 32K (вдвое меньше копий
  на токен) не помогает и после ускорения ядер (64K: −1%, 256K: +1%) — остаётся 16K.
- **Перепаковка весов на каждом подчанке.** Mamba и shared-эксперт считаются кусками по 2048 строк, и NVFP4-вес
  переводился в N4 8 раз на чанк. Кэш на два веса в `wb` (циклы чередуют in/out и up/down): −39 мс ядер на чанк,
  32K +3%.
- **W8A8 на int8 tensor cores** (`nemo_q8.cu`) для Q8_0 attention и BF16 fc1/fc2 вместо BF16-расширения + cuBLAS:
  ядро 390 TOP/s против 233 TFLOP/s cuBLAS на форме 16K×4096×4096, ΔNLL −0.0004 ± 0.0022 (активации по блокам 32,
  как MMQ). В тёплом промпте −16 мс на чанк (узкие k/v с N = 256 плохо загружают карту), но первый промпт после
  загрузки быстрее на ~0.5 с: нет прогрева cuBLAS. Упор ядра — выдача инструкций на скейлы блоков (4 FFMA/FMUL на
  каждый mma k32), а не барьеры: глубина стадии 64 → 128 значений дала +1.5%; трюк «магическое число» вместо
  int→float ничего не дал.
- **Латент экспертов квантовать один раз на токен** (вместо 22 раз — по разу на эксперта) и собирать строки в GEMM:
  квантование −26 мс, но сгруппированный GEMM со сбором строк медленнее на 25 мс — в сумме ноль (проба
  `STRATA_NEMO_LATQ=1`).
- **Роутер на int8** (FP32-вес в Q8-блоки): +0.12% PPL за ~1% скорости — не взят (проба, бит 4 `STRATA_NEMO_Q8`).
- **SSD Mamba**: 256 блоков (голова × половина столбцов), 60 КБ shared — один блок на SM и полторы волны на 170 SM.
  Два блока на SM (PS = 16) медленнее (0.71 против 0.54 мс на 2048 токенов): каждый блок заново грузит B/C и считает
  dt-скан. Строки B/C без паддинга (конфликт банков не более 2-way) — 0.538 → 0.500 мс. Разбиение последовательности
  на сегменты с поправкой состояния по оценке не окупается при одном блоке на SM.

## 4. Чего не делать (проверено и отброшено)

- Готовые 2-битные эксперты (AD-Q2_0_L): PPL +8–12%, а после пропуска промахов по весу NVFP4 ещё и быстрее.
- Кэш экспертов MTP меньше 512 вместе с пропуском промахов: падение принятия черновиков сильнее выигрыша кэша.
- FP8-attention целиком: ошибка в 12–15 раз выше BF16.
- Стриминг KV из RAM для плотной attention (см. п. 2.1).
- Пропуск промахов по весу на промптах 2K–8K без предсказания: отключает упреждающую загрузку и замедляет.
  С предсказанием (роутер следующего слоя на текущем остатке) — ускоряет: 2K 1049 → 816 мс.
- TF32 для роутера: ΔNLL +0.002 и без выигрыша в скорости.
- Чанк 32K для длинных промптов: копий на токен вдвое меньше, но время то же (±1%).
- Сбор строк латента внутри GEMM экспертов вместо квантования на каждого эксперта: выигрыш квантования съедает GEMM.
