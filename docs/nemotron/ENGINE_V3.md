# strata-nemotron: движок v3 — prefill 1270 → 7400 т/с, контекст 1M (2026-10-19)

Цель: догнать по prefill qwen3.8-flash-next в Strata (~4400 т/с на 9K на этой машине) и дать слоту 1M контекста.

Вторая волна (19.10): attention — тайл 128 ключей, экспоненты в FP16, суммы строк через mma с единицами, ленивое
перемасштабирование, упрощённый загрузчик (266 → 312 TFLOP/s-экв.); выход down-проекции экспертов прямо в слоты
(токен, ранг) и одна сумма в порядке рангов (вместо double-аккумулятора); BF16-выход up-проекции; квантование
активаций за один проход из регистров; FP4 GEMM читает ggml-строки экспертов сам (без перепаковки);
shared-эксперт ставится в очередь до синхронизации роутера; C·Bᵀ SSD один раз на группу; пропуск по весу
с предсказанием до 8192 строк; split-K attention с длиной куска, не зависящей от окна (спекуляция снова побитно =
decode).

Третья волна (19.10, тёплый кэш, второй промпт подряд): 128 токенов 98 мс, 2K 2650 т/с, 16K 12 700, 64K 11 270,
256K 7 440 (было 7 050). Сделано: перевод NVFP4-веса в N4 один раз на чанк (а не на каждый подчанк из 2048 строк),
W8A8 на int8 tensor cores для Q8_0 attention и BF16 fc1/fc2 (`nemo_q8.cu`, вместо BF16 + cuBLAS; первый промпт после
загрузки быстрее на ~0.5 с), SSD без паддинга строк B/C (−7% ядра). Prefill 16K–64K теперь одновременно упирается
в счёт (~1.17 с ядер на чанк 16K) и в PCIe (~1.0 с копий), поэтому ускорение отдельного ядра даёт в 2–4 раза меньше
своего вклада; подробности и отброшенное — OPTIMIZATION_NOTES.md. Этапы 7–8 — STAGE7-8_RESULTS.md.

Decode без спекуляции: 98–102 т/с при коротком контексте, 77 т/с на 256K; со спекуляцией 155–163 т/с в чате
(temp 1.0), на 256K до 159 т/с. Перебор MTP после всех правок (длина 4–7 × порог 0.7–0.9) — плато 155–163,
`--spec 5 --spec-min-p 0.8` на нём.

Качество (попарный ΔNLL по токенам, wikitext 40 × 1024):
- W4A4 (FP4 tensor cores во всех NVFP4-GEMM prompt'а): +0.0028 ± 0.0019 (PPL ×1.003); decode не затронут.
- int8-K/FP16-V attention: prompt +0.0035…0.0049 (×1.004–1.005); decode-путь против v2: −0.0033 ± 0.0020 (не хуже).
- `--prompt-skip-w 0.3` (только чанки ≤ 1024 строк): ×1.005; τ = 0.2 бесплатно, τ = 0.4 ×1.014.
- Prompt детерминирован: результат не зависит от содержимого кэша экспертов (сумма экспертов в double);
  greedy со спекуляцией побитно = обычный decode (300/300).

## Что сделано (в порядке вклада)

1. **FP4 tensor cores (W4A4)**, `nemo_fp4.cu` (отдельная библиотека под sm_120a):
   `mma.sync ... kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64` — NVFP4 × NVFP4 со скейлами ue4m3 на 16 значений.
   Активации квантуются построчно (глобальный скейл amax/(448·6), e4m3 на 16 значений, e2m1 RNE), веса
   перепаковываются из ggml/tiled в «естественный» порядок полубайтов (N4). Блок 128×128, k = 128 на стадию,
   3 стадии cp.async, ldmatrix для фрагментов: 792 TFLOP/s на форме in_proj (пик mma 1610; cuBLAS BF16 ~150).
   Эксперты — сгруппированный запуск по списку тайлов. Тест `nemo_fp4_parity`: квантование = хост побайтно,
   GEMM против float64.
2. **Копии экспертов параллельно счёту**: промахи идут по своему потоку в кольцо из 384 блобов (или в пустой слот
   кэша), следующий MoE-слой планируется заранее (на чанке ≥ 512 строк нужны почти все эксперты), считаются
   сначала попадания. Метаданные слоя — одной копией из pinned-памяти (раньше pageable-копии на каждую группу
   останавливали хост).
3. **Attention на tensor cores**: K в кэше int8 со скейлом на (ячейку, kv-голову), V в FP16; Q·K — int8 mma
   (m16n8k32, 806 TOP/s), P·V — FP16 mma с FP16-суммой на тайл 64 ключей, затем FP32. Варп = 16 голов одного токена
   над общей KV-головой (GQA 16:1). На 8K 440 → 17 мс; на 256K 30 → 19 с. Decode/окно проверки на контексте
   ≥ 16K ключей — тот же код split-K (блок читает ключ один раз для всех токенов окна): decode на 256K 80 → 159 т/с.
4. **Mamba**: чанковый SSD (Q = 32, FP32 на CUDA-ядрах, состояние в регистрах, предвыборка чанка) для T ≥ 64;
   последовательный scan (побитно = decode-шаг) для окон проверки. 245 → 117 мс на 8K.
5. Хвосты буферов чанка (строки 8192–16383), пока чанк не длиннее 8192, отдаются кэшу экспертов в долг (+4 слота);
   длинный чанк забирает их обратно.
6. Короткие промпты с пропуском (≤ `--prompt-skip-max`): роутер следующего слоя на текущем остатке, его вероятные
   промахи (вес ≥ τ) копируются заранее (`STRATA_NEMO_PROMPT_PRED`): 2048 токенов 933 → 819 мс, 4096 1184 → 946 мс.
7. Мелочи: роутер через SGEMM (343 → 10 мс), быстрые ядра деквантования, планирование MoE на хосте сортировкой
   подсчётом (9.5 → 4 мс на слой при чанке 16K), чанк 16K (на длинных промптах вдвое меньше копий на токен),
   буферы групп ≥ чанка (при 16K один эксперт может взять > 8192 строк — это был выход за границу, исправлено).
8. **Пропуск промахов в коротком prompt'е** (`--prompt-skip-w τ --prompt-skip-max N`): промах, чей наибольший
   вес в чанке < τ, не копируется. Короткий prompt задевает почти все 512 экспертов слоя (~40 ГБ по PCIe), и время
   задаёт копирование, а не счёт: 128 токенов 0.7 с → 85 мс.

## Контекст 1M

У Nemotron attention плотная: каждый шаг decode читает весь KV (на 1M ~6.5 ГиБ). Стриминг KV из RAM, как у
flash-next (у неё разреженная QSA-attention), дал бы ~0.2 с на токен. Поэтому KV живёт в VRAM, но эластично:
страницы по 65 536 ячеек на каждый attention-слой и MTP; сверх `--kv-base` (65 536) страница добавляется, когда
контекст до неё дорастает, а память под неё отдаёт кэш экспертов (полосы по 4 слота каждого слоя); на следующем
диалоге (`reset`) страницы возвращаются кэшу. Ядра адресуют ячейку через таблицу страниц в параметрах (до 64).
Короткие диалоги этого не замечают; кэш экспертов: 140 слотов на слой при 64K, 128 при 256K.

«Иголка в стоге сена» через llama-swap (`tools/needle_bench.py`, глубины 10/50/90%, greedy):

| длина | найдено | prefill | слотов на слой | KV |
|---|---|---:|---:|---:|
| 32K | 3/3 | 4.4 с (7600 т/с) | 140 | 64K |
| 128K | 3/3 | 18 с (6950 т/с) | 132 | 128K |
| 256K | 3/3 | 47 с (5560 т/с) | 128 | 256K |
| 512K | 3/3 | 117–125 с (~4300 т/с) | 112 | 512K |
| 1M (1 027 882 токена) | 3/3 | 374 с (2750 т/с) | 84 | 1M |

После 1M-запроса новый короткий диалог возвращает KV к 64K, а кэш — к 136 слотам. 1M-запрос на 1 053 087 токенов сервер
корректно отклоняет (400: промпт + max_tokens больше окна, без обрезки).

Слот отдаёт контекст: `/v1/models` `meta.n_ctx`, `/props` `n_ctx`, `/health` `max_context` = 1048576; в списке
llama-swap — «Strata v3 + MTP, 1M».

## Ключи движка (новые)

`--kv-base N` (начальный KV), `--prompt-skip-w τ --prompt-skip-max N`, `--chunk 16384`. Переменные для проб:
`STRATA_NEMO_FP4` (биты: 1 плотные, 2 up экспертов, 4 down; 0 — BF16+cuBLAS), `STRATA_NEMO_RING`,
`STRATA_NEMO_ATTN_TC_KEYS` (порог tensor-core attention в decode), `STRATA_NEMO_SEQ_SCAN`, `STRATA_NEMO_A4`
(эмуляция W4A4 в BF16-пути), `STRATA_NEMO_HOSTPROF`.

Тесты: `nemo_fp4_parity`, `nemo_gemm_parity` (+ построчный деквант NVFP4), `mamba_parity` (+ SSD против эталона и
против последовательного scan на 2000 строк), `attn_parity` (постраничный KV, int8-K), `nemo_iq_parity`,
`moe_parity` — PASS. Бенч attention: `nemo_attn_bench [p0] [T]`.

## Не сделано / дальше

- Attention на ~40% теоретического потолка (упор в регистры: 1 блок на SM, фазы mma/softmax не перекрываются);
  на 1M prefill — минуты, attention там основное время.
- Скейлы int8-K/Q по группам из 32 вернули бы часть ×1.004 attention ценой ~20–30% её скорости.
- Промпты 1K–8K всё ещё упираются в ~1 с копий экспертов (пропуск по весу там мешает упреждающей загрузке).
- Перепаковка экспертов в N4 на каждой группе (~90 мс на 8K) и квантование входа up по строкам (22× повтор)
  можно убрать, читая ggml-формат прямо в GEMM.
